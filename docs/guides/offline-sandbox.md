# Offline sandbox

The repository publishes a self-contained copy of its Pixi environment to a Git orphan branch. A host without network access restores that branch and runs the locked environment with no package registry. The transport comes from [Pixi Sandbox](https://archont561.github.io/pixi-sandbox/) and no custom wrapper is added here.

## Files

| Path | Owner | Purpose |
| --- | --- | --- |
| `pixi-sandbox.toml` | Reviewed by hand | Publish plan: one bundle, one platform, and the workflow policy |
| `.github/workflows/publish-sandbox.yml` | Generated | Packs, verifies, and force-pushes the transport branch |
| `.github/workflows/relock.yml` | Generated | Refreshes `pixi.lock` for a manifest edit made on a disconnected host |
| `restore.sh` | Generated | Airlock launcher: fetches the branch, verifies it, and restores the environment |

The three generated files carry the `Generated by pixi-sandbox init` marker and a `pixi-sandbox-version` stamp. Run `pixi-sandbox init` to regenerate them, and never edit them by hand. The generator never rewrites `pixi-sandbox.toml`. That file is reviewed data, so a change to the plan is a reviewed change.

## Publishing

The publisher runs on a push to `main` that changes a transport input: `pixi.toml`, `pixi.lock`, `package.json`, `bun.lock`, or `pixi-sandbox.toml`. A weekly schedule and a manual dispatch run it as well.

```sh
gh workflow run publish-sandbox.yml --ref main
gh run watch "$(gh run list --workflow publish-sandbox.yml --limit 1 --json databaseId --jq '.[0].databaseId')"
```

The job downloads the pinned `pixi-sandbox` release, verifies the checksum, installs the `default` environment, packs it, runs `doctor` against the reviewed budgets, and force-pushes the result to `sandbox/developer-linux-64`. Confirm the branch after the run:

```sh
git ls-remote --heads origin 'refs/heads/sandbox/*'
gh api repos/Archont561/polyglot-clean-code/branches --jq '.[].name | select(startswith("sandbox/"))'
```

## Restoring

On the airlocked host, with the repository and its `sandbox/developer-linux-64` branch present:

```sh
bash restore.sh
export PATH="$HOME/.local/bin:$PATH"
pixi install --frozen --offline
pixi run --frozen doit ci
```

The launcher reads the branch from `pixi-sandbox.toml`, fetches only the `sandbox/*` namespace when the branch is missing, verifies the transport against its manifest, and registers the packed tools for the current user. Set `PIXI_SANDBOX_FETCH=skip` when the branch is already in the clone, and `PIXI_SANDBOX_USER_TOOLS=skip` on a shared host that must not touch the user `PATH`.

## Reviewing a relock commit

When `pixi lock --check` fails on a pull request, `relock.yml` solves the environment with the Pixi version the generator pins, commits the refreshed `pixi.lock` as `pixi-sandbox[bot]`, and dispatches the guard, `ci.yml`, and the publisher on the repaired commit. A re-solve takes the newest build each constraint allows, so the commit can carry version bumps beside the lock refresh. Review it the way you review any dependency update. The bot commits with the `lock` scope, which `.versionrc` reserves for it.

One hand-off cannot finish before the merge: a pull request that introduces `publish-sandbox.yml` finds no such workflow on the default branch, so the dispatch and its verdict report a failure until the publisher exists on `main`. Merging the lane is what makes that verdict runnable.

## Limits

- The bundle targets `linux-64` only, because that is the platform list in `pixi.toml`.
- The transport carries the packed environment, not the repository history. A restore still needs the checkout and the sandbox branch.
- `pixi-sandbox` is published on the `archont561` prefix.dev channel. Installing it on a connected host needs that channel and `conda-forge`.
- Regenerating the files after a tool upgrade keeps the version stamp and the templates in step. Run `pixi-sandbox init --check` in a connected clone to report drift before it reaches a pull request.
